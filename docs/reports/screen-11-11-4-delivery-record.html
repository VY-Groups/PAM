4. Behaviour contracts (as proven by tests)

  • Emergency state machine — verbatim. Sealed (sealed - emergency-admin grants nothing / …awaits two approvals) or window OPEN - …; the grants line renders em-dash in flight, N grant(s) on record, no grants on record; the open button is disabled exactly when !data || pending > 0 || open > 0.
  • Prompt parity. window.prompt asks for the reason with the verbatim fallback line; a null cancel makes no request; a transport failure of the open attempt renders the legacy request refused: <error.message> (message passthrough).
  • Refusal keyed to the snapshot. The refusal is stored against a snapshot field (no useEffect — satisfies react-hooks/set-state-in-effect); it clears on onSuccess invalidation or any fresh read.
  • ConnectorNote precedence. Error wins over every branch (matches the 11.1 chips); the connected branches are contract-driven and deliberately unasserted — a pristine rig never reports them (documented like the SMTP 200 arm).
  • settingsLive. Cluster state {reachable:true, role, …overview}, skeleton {reachable:false, role:'unknown'}; RBAC {reachable, roles, bindings}; load awaits invalidateQueries; both deleted on unmount. EmergencyCard carries data-role="emergency-state|emergency-grants|emergency-open" + testids so the 11.5 gate re-point reads React instead of the legacy page.
  • Actions. Strict 11.3 precedent — error.message verbatim; BackendDown renders the shared settings.forms.actions.unreachable; the LDAP bind password is never echoed, cleared on success, and the one-time ticket box only enters the DOM after a real success.
  • MFA enrol. The secret box enters the DOM only after a real 201 (fixture secret is the redacted stand-in, house rule) and a failed re-enrol keeps the minted factor.

7. The capture-drift saga (honest record)

  1. 11:08 UTC — the drift. The 11.4 capture cycle called POST /mfa/enroll on rig5100 to capture the real 201 shape. That endpoint generates a genuine TOTP factor and writes it into the settings mfa group's readonly fields (factor_enrolled_for=admin, factor_secret=<set>, factor_created_at=… — changelog actor admin).
  2. 13:19 UTC — the gate fails (1 check). 89 PASS, 1 FAIL: the Hub 8a flow's POST /sessions step returns 403 TOTP code required - a factor is enrolled. The session-start risk gate calls _mfa_band_gate → mfa_status(), which reads exactly that settings row. This supersedes the earlier claim “no gate check touches the factor”: settings-screen checks don't, but the Hub 8a session gate does.
  3. Planned remedy — and why it was wrong. The standing plan was DELETE /api/v1/auth/mfa/factors/<id>. Reading the contracts first (routes.py:3327, mfa.py:219, identity.py) showed the mismatch: that route deletes from the identity mfa_factors table, which is empty — POST /mfa/enroll (the legacy-facing enrol the page captures) writes only the settings row. The identity table was always empty: POST /auth/login as admin succeeded with no MFA challenge; only the risk band at session start refused.
  4. Diagnosis (no guesses). SETTINGS_SCHEMA['mfa'] marks all factor_* fields readonly: True — PUT /settings/mfa rejects them; no disarm/reset route exists anywhere in the API; GET /settings/mfa 404s (the served shape is {schema, settings} via GET /settings — an early PowerShell read of $null printed as empty and was caught by re-reading the raw JSON); the sqlite probe confirmed the empty identity table.
  5. Fix — the app's own routine, not raw SQL. Temp/vypam-rig/disarm_mfa_114.py runs inside the container and calls _persist_settings('mfa', …) — the exact routine mfa_enroll itself writes through, whose docstring states the MFA endpoints “keep the same changelog discipline”. One SettingsEvent records the clearing (actor rig-maintenance, 13:54:51, old→new honest) and the audit trail itself is never touched. Verified after: settings.mfa reads all empty on 5100; rig5101 was already pristine (stored=False).
  6. Side upkeep, documented. The cleanup script rotated both rigs' console-admin passwords through the API's own path (password-reset → forced-change → login → logout); the gate authenticates via X-Admin-Token, not the password, and both post-fix gate runs prove nothing else depended on it. The gate's earlier 401 on auth/mfa/factors (“Console session required”) is why the honest API sequence establishes a session first — _stepup_if_human passes machine/token sessions (routes.py:2866).
  7. Proof. Re-ran the gate in both modes: 5100 83/0, 5101 90/0, ALL CHECKS PASSED ×2 — the Hub 8a session step now through.
